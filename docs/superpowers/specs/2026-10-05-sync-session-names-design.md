# 同步清单短名称与兼容升级设计

日期：2026-10-05。目标是消除固定 rclone 1.75.1 将双端完整根路径拼入 bisync 状态文件名造成的 Windows 单文件名超限，同时保留过滤、冲突、删除门禁和服务器文件任务恢复。

## 根因与选择

`bilib.SessionName` 使用两端完整 FsPath；更换 workdir 只改变父目录。alias 会展开真实根，union 要求至少两个 upstream。缩短配置根只规避问题，不能作为产品修复。

采用固定版本自带的 combine 后端：每端只配置一个名为 root 的映射，bisync 使用 `localview:root/`、`remoteview:root/`。真实目录、SSH backend、正文位置不变，无挂载、软链接、服务器安装或新增依赖。本机原始长路径探测失败，combine 初始化和双向增量探测通过。

## 驱动与编码

只有 bisync 使用短逻辑根。清单读取、正文读取、移动、删除和任务拉取继续使用真实 workspace backend。每次 bisync 按 `options.localDir` 或工作区目录生成 localview，避免绑定错误镜像；remoteview 指向已核对的真实远端根。

`upstreams` 使用 rclone 的空格分隔 CSV 语法：整个 `root=实际目录` 用双引号包围，内部双引号翻倍，反斜杠保持原样。Windows 本地路径规范为正斜杠；不使用 JSON 或 shell 引用。

映射通过子进程环境传入，不写 rclone.conf。额外环境只对本次调用有效；复制的 SSH 密码/私钥在调用 finally 清除，context 原环境仍按已有 close 生命周期清除。取消和认证代际检查沿用原流程。

## 旧基线与持久文件任务

目标 `signature` 保持原有 mirror-v1 算法。它标识实际目标，不能因工具内部布局升级改变，否则旧服务器文件任务会被误判为目标变化。

驱动增加可选 `baselineLayout`，真实驱动固定为 `combine-v1`；状态增加可选非空、最长 64 字符的同名字段。旧状态可正常加载。

已有 signature、布局不匹配且未明确初始化时，普通同步在读取远端清单、传输、删除或执行前返回 recovery 确认状态，保留原基线和旧 rclone 清单。现有初始化 HTTP 接口仍要求 confirmed=true；经原有双端差异保留后 resync 新清单。首次工作区沿用原初始化门禁，成功回写后才保存布局标记。

未完成服务器文件任务仍以实际目标签名核对，通过原任务恢复入口拉取独立快照、远端优先重建固定镜像基线、应用本地变更后保存新布局。目标真的变化仍拒绝恢复，不重放服务器写操作。升级不删除或手工重写旧清单。

旧状态若正在等待删除确认，批准或拒绝入口同样先检查布局；不读取远端清单、不恢复文件、不清空待删除元数据。界面明确提示本次删除请求尚未处理，确认升级恢复会重新拉取这些文件，恢复后重新核对删除。元数据保留至明确升级成功，不将此时的删除点击作为初始化批准，也不暗中取消已接受的删除。

## 验收与交付边界

覆盖长本机配置根、中文/空格/双引号映射，初始化与增量、过滤、冲突、删除、执行门禁、旧基线升级及旧持久任务恢复。CSV 编码须原样保留反斜杠；Windows 版 rclone 的 fspath.Parse 会把远端根中的反斜杠转换为斜杠，真实反斜杠目录受此既有限制，实际探测停在原 workspace 清单读取，不能标为 combine 验收通过。使用随机临时目录和已授权 SSH 目标；真实信息仅在 ignored 报告中。

Native 实施，一次新的独立核心 Review 后补最少核心回归；不续接历史代理，不调用 gpt-6-astra，不重复未受影响验收。通过后更新正式文档，提交到 codex/sync-session-names，PR 合入 feat/ssh-workflow，再以 no-ff 合入 main，双平台 CI 通过后仅清理已合并小分支。仍被策略阻断的原生界面验收不重试，整个 Goal 保持进行中。
